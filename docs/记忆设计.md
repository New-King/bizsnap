# 记忆设计

## 一、为什么是两张表

| 表 | 回答的问题 | 内容 |
| --- | --- | --- |
| `contacts` | 这个人**现在**是什么状态 | 当前值 + 每条属性的变更时间线 + 检索列 + 向量 |
| `interactions` | 这个人的关系**发生过什么** | 事件、原因、来源、见过面的记录 |

两者的边界只有一条：**值放 `contacts`，故事放 `interactions`**。

试过但被否掉的三种做法：

- **加一张 `briefing`（关系纪要）**：要回答「什么时候重写」，而重写是有损压缩，几轮之后细节会被磨平，且每次确认多一次模型调用。
- **在 `interactions` 里再存一份 `changed` / `facts`**：与 `attributes.history` 重复，形成两份可能对不上的账。
- **给消息建向量（`semanticRecall`）**：召回的是句子，不带「这人是谁」的归属，跨会话会把客户 A 的话安到客户 B 头上。

## 二、属性时间线（SCD2）

一条属性就是一条时间线：

```ts
{
  type: 'industry',
  value: '建筑设计',            // 当前值
  since: '2025-12-12',          // 当前值从哪天生效
  history: [                    // 旧值，区间不重叠
    { from: '2013-12-05', to: '2025-12-11', value: '房地产销售' }
  ]
}
```

确认一次更新时：

1. 有新值 → 把旧 `value` 压进 `history`，`to` = 新 `since` 的**前一天**（用 `2025-12-11` 而不是 `12-12`，避免区间重叠）
2. `value` 换成新值，`since` = 今天
3. 值没变 → 整条不动
4. `history` 只增不删；超过 10 段时把最早的几段合并为一段 `{ from: 最早, to: 某日, value: '此前：房地产销售' }`

`history` 是 `interactions` 的物化投影，**只能由确认接口派生**。任何地方不许手改它；需要核账时以 `interactions` 为准。

## 三、检索：三种匹配 + 一条向量

`contacts` 上存两个派生的检索列，确认时重算：

```
searchCurrent: "王建国 建筑设计 合规总监 SaaS 集团 项目X"
searchHistory: "房地产销售 跨境支付 合规"
```

`search_contact` 的查找顺序：

1. 姓名 / 电话 / 公司 LIKE `searchCurrent` → `matchedIn: 'now'`
2. LIKE `searchHistory` → `matchedIn: 'history'`
3. 上面命中少于 3 个时，把 query 嵌入，与全表 `embedding` 算余弦 → `matchedIn: 'semantic'`

`when` 参数由 agent 自己决定：

- `any`（默认）：三种都返回，候选带 `matchedIn`，模型能看出这个匹配是「现在」还是「以前」
- `now`：丢掉只命中 `searchHistory` 的候选，用于「现在谁在做支付」这种问法

**向量只负责找到是谁**。命中后返回 `contactId` 与候选人信息，公司、职位、哪天变的、为什么变的，一律回 DB 查。向量结果绝不出现在回答正文里。

嵌入模型固定 `BAAI/bge-large-zh-v1.5`（1024 维）。换模型等于换维度，所有人要重灌——所以不换。

## 四、background：为什么变

`interactions.background` 是这套记忆里唯一带「人情味」的字段：客户是自己跳槽还是公司被并购、这条消息是从截图看到的还是用户口述的、顺带提到了什么。

**它只允许复述输入里明确出现的原因。** 没有就写空字符串。两道关卡：

- `prompt.ts` 里明确要求，并给反例
- `services/confirm.ts` 里做一次字符串校对，本轮输入（截图文字 + 用户那句话）里找不到依据就置空，并打 warn

`background` 的来源是工具入参里的 `reason`：模型只能复述，不能自己补。校对规则（`groundBackground`）：

1. 去掉空白与中英标点后，`reason` 整段出现在输入里 → 通过
2. 否则把 `reason` 切成三字片段，命中率 ≥ 50% → 通过（容忍模型做了轻微改写）
3. 都不满足 → 置空 + `console.warn`

本轮输入取的是该会话里**最后一条 user 消息**。

卡片是只读的，用户没有别的机会纠正，所以这条不能松。

## 五、写入路径

五个工具全部只读或只出草案：

- `search_contact` / `get_contact_history`：读
- `create_contact` / `update_contact` / `create_meeting`：返回草案对象，不碰数据库

**写库只发生在 `POST /api/threads/:id/confirm`**，事务包住：

```
多条 interaction  →  attributes 时间线（封口 + 新值）
```

任一环节失败整体回滚，不留半写状态。

`searchCurrent` / `searchHistory` / `embedding` 是派生物，在**事务提交之后**重算：嵌入要发 HTTP 请求，占着写锁等网络会把并发确认卡死；嵌入失败也不该让联系人写不进去（该人暂时不参与语义检索，关键词检索照常）。

确认成功后还会写一条 `confirmed_cards`（`card_id` 主键），让 iOS 刷新会话时仍能把卡片渲染成「已写入」，不用把状态塞回消息体里。

确认接口是流式的，但**落库与流无关**：事务提交先于任何文本推送，`written` 帧只是把结果告诉客户端，洞察是事后的解释、不落库。

## 五之二、会话数据放哪

| 表 | 谁写 | 内容 |
| --- | --- | --- |
| `threads` | 业务代码 | 会话标题、主联系人、最后一条消息摘要 |
| `messages` | 业务代码 | 展示用的消息：文字、用户图 base64、卡片草案 JSON |
| `confirmed_cards` | 业务代码 | 已确认的卡片 id |
| `mastra_*` | Mastra `Memory` | 真实的对话上下文，`lastMessages: 20` |

两套并存是刻意的：`messages` 是**给人看的账**（要带图、要带卡片、要刷新后还原），`mastra_*` 是**给模型看的上下文**（Mastra 自己管裁剪）。业务记忆（`contacts` / `interactions`）与这两者都正交。

## 六、禁止行为

- 工具里写库（会让模型幻觉直接污染长期记忆）
- 手改 `history` 或检索列（它们是派生物）
- 让模型生成没有输入依据的 `background`
- 用聊天消息向量做跨会话召回
- 把洞察落库（洞察是实时表述，不是事实）
