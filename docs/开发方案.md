# 开发方案

## 一、产品定位

面向商务人士的 iOS 轻量 CRM。以会话为单位与 agent 对话，用户可以上传商务聊天截图、也可以只打一段文字，agent 读懂其中的联系人、公司、职位、约定，主动查通讯录与历史记忆，生成可确认的行动卡片；确认后真实写入系统通讯录与日历，并把事实沉淀成按人索引、带时间线的长期记忆。

## 二、核心交互

- **会话式**：首页是会话列表，每个会话只服务一个客户，上下文互不干扰。会话内可继续追问（「他上次说预算多少」「帮我起草个跟进消息」）。
- **统一输入**：图片（相册/拍照，可选）与文字（可选）走同一个入口，是否产生卡片由模型判断；纯文字不传图也能触发联系人更新。
- **主动查人**：新会话里只报一个名字或一句描述，agent 自行调用查询工具，判断此人是否已存在、是否有历史，再决定新建还是更新。
- **三类卡片**：创建联系人、更新联系人、创建会议。**卡片只有固定文案 + 勾选框，不显示任何字段**。
- **卡片只读、只认最新**：不能编辑；只有最后一条带卡片的 agent 回复可勾选，更早的卡片一律置灰。
- **信息不全就追问**：缺关键信息时 agent 在对话里问，不在卡片上标「待补充」。
- **非商务输入拒绝**：生活闲聊、表情包、广告、代码截图明确提示「未识别到商务信息」。

### 卡片只有固定文案带来的硬约束

既然卡片上不写具体内容，**agent 的正文必须把本次要写入的内容说清楚**：建谁、改哪一项、什么时间、哪些人参加。否则用户看到「创建联系人」四个字，不知道自己确认的是什么。信息不够就先追问，不生成卡片。

## 三、技术选型

| 层 | 选型 | 说明 |
| --- | --- | --- |
| iOS | SwiftUI + iOS 17+，XcodeGen 管工程 | 声明式 UI，`project.yml` 避免手改 pbxproj |
| 系统能力 | PhotosUI、Contacts、EventKit | 原生框架，无第三方依赖 |
| Agent | `@mastra/core@1.80`、`@mastra/memory@1.39`、`@mastra/libsql@1.27` | 只用 `Memory` 的会话消息持久化与 `lastMessages`；不装 `mastra` CLI |
| 模型 | `deepseek-flash` via `@ai-sdk/deepseek@3`（`ai@7.0.156`） | 支持图像理解 + Tool Calls |
| 嵌入 | 硅基流动 `BAAI/bge-large-zh-v1.5`（1024 维）via `@ai-sdk/openai-compatible@3` | 必选，缺 key 启动即报错 |
| HTTP | Hono 4 + `@hono/node-server` + zod 4 | 薄路由层。两个会出字的接口都走 SSE：`streamSSE` 直接给帧与心跳，不用自己拼 `res.write` |
| 存储 | LibSQL 单文件 `bizsnap.db` | Mastra 的 thread/message 表与两张业务表同库 |

### 明确不用

- **`workingMemory`**：默认 `scope: 'resource'`，是「按用户」而非「按联系人」的维度，与本项目不重合。时区、默认会议时长等直接写进 `config.ts` 常量。
- **`semanticRecall`**：召回的是聊天消息，不带「这人是谁」的归属，跨会话召回会把客户 A 的话安到客户 B 头上；且用户删会话后索引失效。跨会话找人改由 `search_contact` 查表。
- **`LibSQLVector` / `@mastra/rag`**：几百个联系人的向量在 Node 侧算余弦足够，不引向量库。
- **`briefing` 关系纪要**：要维护「什么时候重写」这个说不清的触发条件，改由每条事件自带的 `background` 承载。
- **`preferences` / `userEdited`**：没有消费方，卡片也不允许编辑。
- **洞察的「依据」行、独立的洞察消息类型**：agent 的普通文字就是洞察，不再单设一种消息。

## 四、数据模型（两张业务表）

### `contacts` —— 状态

```ts
export type AttributeType = 'industry' | 'company' | 'position' | 'project' | 'relation';

// 一条属性 = 一条完整时间线
export type Attribute = {
  type: AttributeType;
  value: string;                 // 当前值
  since: string;                 // 当前值生效日，ISO 日期
  history: { from: string; to: string; value: string }[];  // 旧值，区间不重叠，最多 10 段
};

export type ContactRecord = {
  id: string;                    // 归一化姓名 hash
  name: string;
  phone: string;                 // 不建时间线，覆盖最新值，变更在 interactions 留痕
  email: string;
  attributes: Attribute[];
  searchCurrent: string;         // 派生物："王建国 建筑设计 合规总监 SaaS 集团"
  searchHistory: string;         // 派生物："房地产销售 跨境支付 合规"
  embedding: number[] | null;    // 对 searchCurrent + searchHistory 拼接后嵌入，一人一条
  lastContactAt: string;
  interactionCount: number;
};
```

### `interactions` —— 事件

```ts
export type Interaction = {
  id: string;
  contactId: string;
  groupId: string;                      // 同一次确认产生的多条共享
  at: string;                           // ISO 8601
  kind: 'created' | 'updated' | 'meeting';
  source: 'image' | 'text' | 'both';
  attrs: string[];                      // 这次动了哪些属性，只存名字，如 ['company']
  background: string;                   // 为什么；只复述输入里出现的原因，没有就空字符串
  meeting?: {
    title: string;
    startTime: string;
    endTime: string;
    location: string;
    participants: string[];
  };
};
```

**为什么是两张**：`changed` / `facts` 快照删掉，值一律回 `attributes` 查，避免两份对不上的账；会议不产生属性变更，`attributes` 里没有它的位置，必须由 `interactions` 承载。

**会议归属**：一条会议只存一条记录，挂在当前会话的主联系人名下。`participants` 存名单，展示时 1 人写名字、2 人写「张三、李四」、3 人以上写「张三等 4 人」。

## 五、记忆规则

1. **属性时间线（SCD2）**
   - 有新值 → 旧 `value` 压进 `history`，`to` = 新 `since` 前一天；`value` 换成新值，`since` = 今天
   - 值没变 → 不动
   - `history` 只增不删；超过 10 段把最早的几段合并成一段「2013 年前：房地产销售」
   - `history` 是 `interactions` 的物化投影，只能由确认接口派生，不许手改；对账以 `interactions` 为准
2. **background 不许模型编**：只复述输入里明确出现的原因，没有就写空字符串。prompt 约束 + 服务端校验双保险。
3. **写入只有一条路径**：五个工具全部只读或只出草案；写库只发生在 `/api/threads/:id/confirm`，一个事务包住「多条 interaction + attributes 时间线更新」，检索列与向量在提交后重算（嵌入要发网络请求，不该占写锁）。
4. **向量只负责找人**：命中后返回 `contactId` 与候选人信息，事实一律回 DB 取，向量结果不出现在回答正文里。

## 六、五个工具

| 工具 | 关键入参 | 行为 |
| --- | --- | --- |
| `search_contact` | `query`、`when?: 'now' \| 'any'` | ① 姓名/电话/公司 LIKE `searchCurrent`；② LIKE `searchHistory`；③ 命中少于 3 个时用 query 向量找补。返回候选含 `now` / `timeline` / `matchedIn`。`when='now'` 时丢掉只命中历史的候选 |
| `get_contact_history` | `name`、`limit?`（默认 8） | 该人 `attributes` 全时间线 + 最近 N 条 `interactions` |
| `create_contact` | name / phone / email / industry / company / position / project / relation / `reason?` | 只返回卡片草案，不写库；库里已有同名时返回 error，让模型改用 `update_contact` |
| `update_contact` | `target_name` + 要改的字段 + `reason?` | 只返回卡片草案；`changes` 只含真正变化的字段，全无变化时返回 error |
| `create_meeting` | title / start_time / end_time / participants / location / remark / `reason?` | 只返回卡片草案；时间必须带时区 ISO 8601，省略结束时间按 1 小时 |

`maxSteps: 5` —— 允许「查人 → 查历史 → 出卡片」三步推理。
用 Mastra 原生的 `maxSteps` 而不是 `ai` 的 `stopWhen: stepCountIs(5)`：`ai@7` 的 `StopCondition` 泛型与 Mastra 内部的 `StopCondition` 不兼容，编译不过，运行时语义一样。

三个出卡工具都带 `reason`：模型把输入里的原话填进来，`/api/threads/:id/confirm` 校验它能在本轮输入里找到依据，找不到就置空——这是 `background` 不出现幻觉的执行点。

工具在 Mastra 里的注册名（也就是模型看到的 `toolName`）必须用下划线小写：`search_contact` / `get_contact_history` / `create_contact` / `update_contact` / `create_meeting`。从 `toolResults` 里捞卡片时靠这个字符串判断。

## 七、接口

| 接口 | 入参 | 出参 |
| --- | --- | --- |
| `POST /api/threads` | `{ title? }` | `{ threadId }` |
| `GET /api/threads` | — | `[{ id, title, contactName, lastMessage, updatedAt }]` |
| `GET /api/threads/:id/messages` | — | 消息数组（文字 / 图片 / 卡片） |
| `POST /api/threads/:id/messages` | `{ text?, imageBase64?, contactsSnapshot? }` | `text/event-stream`：`start` → 若干 `text`（增量）与 `card`（工具一返回就推）→ `done`（落库后的完整消息）；失败推 `error` |
| `POST /api/threads/:id/confirm` | `{ cards: [{ id, kind, reason?, payload }] }` | `text/event-stream`：`written`（落库结果，先到）→ 若干 `text`（洞察逐字）→ `done` |
| `PATCH /api/threads/:id` | `{ title? }` | `{ ok }`，会话改名 |
| `DELETE /api/threads/:id` | — | `{ ok }`，连消息一起删 |
| `POST /api/demo/seed` | — | `{ contacts, interactions }`，灌演示数据（幂等） |
| `POST /api/demo/reset` | — | `{ ok }`，清空业务数据 |

`contactsSnapshot` 只在首次进入 app 或通讯录变更后上传（最多 200 条，仅 name / company / position / phones）。

`insight` 只回给前端展示，**不写入**会话消息表：它是对这次写入的即时解读，不该在下次打开会话时再冒出来一遍。

## 七之二、流式约定

两条流共用一套帧格式：一行 `data: <json>`，JSON 必带 `type`；不使用 SSE 的 `event:` 名，客户端只按行读、只认 `data:` 前缀。心跳交给 Mastra 的 `withSseHeartbeat`（`: heartbeat` 注释帧，只在空闲时插）。

- **文字**：`text-delta` 直接转发成 `text` 帧，客户端自己拼
- **卡片**：`tool-result` 一到就推 `card` 帧——卡片比正文先出现，用户不用等到回复结束才知道要建什么
- **收尾**：`done` 帧带落库后的完整消息 / 洞察，客户端以它为准覆盖增量
- **中断**：客户端断开 → 停止消费上游、删掉本轮用户消息、不写 assistant 消息

**为什么不用 `@mastra/ai-sdk` 的 `handleChatStream`**：它输出的是 AI SDK 的 UI Message Stream（还分 v5 / v6 / v7），只覆盖聊天这一条；`/confirm` 那条流（先 `written` 再逐字洞察）它管不了，硬用会变成两套帧格式，Swift 端要写两个解析器。这里只要一套稳定的 5 帧协议，所以自己从 `agent.stream().fullStream` 映射；心跳是唯一复用的部分。将来要给网页版 `useChat` 用，再换成 `handleChatStream`。

## 八、确认流程

1. 用户勾选一张或多张最新卡片，底部出现「确认选中 N 项」
2. 点击后，服务端逐张落库：能写的都写，写不了的（比如目标联系人不存在）在 `written` 里标 `ok: false` 并带原因，不影响其它卡
3. 事务一提交就推 `written` 帧，客户端立刻逐条写系统通讯录 / 日历；某条失败只影响那一条，标红并给重试
4. 洞察在 `written` 之后逐字流出，不阻塞系统写入：日历没权限也不耽误看洞察

顺序不能反过来：系统通讯录写错没法撤回，所以以本地库为准。
事务只包住数据库写入。检索列与向量的重算放在事务之后：嵌入要发 HTTP 请求，占着写锁等网络会把并发确认卡死；嵌入失败也不该让联系人写不进去。

## 九、关键约束与风险

- **两个外部依赖各有一个自检脚本**：`check-vision.ts`（图片是否透传，不传图时会现场画一张 512×512 PNG，不通则改 `createOpenAICompatible({ baseURL: 'https://api.deepseek.com' })`）、`check-embedding.ts`（键有效、维度 1024）。两个脚本都用 `node:` 内置模块 + `fetch`，不依赖 server 的 node_modules
- **检索列与向量是派生物**：只在确认流程里重算（事务提交之后），任何读取路径不许写
- **卡片只认最新**：按「最后一条含卡片的 agent 回复」判定可点；其余 40% 透明、勾选禁用。用户问一句、agent 只回文字时，上一张卡仍可点
- **时间基准注入**：prompt 带 `now` / `timezone` / `weekday`，要求输出带偏移 ISO 8601；iOS 写 EventKit 前用 `ISO8601DateFormatter` 校验
- **模拟器通讯录为空**：设置页「填入演示联系人」，覆盖「换行业 / 换公司 / 换职位」三类变化
- **LibSQL 并发**：单文件库，确认全程一个事务
- **联系人同步范围**：Contacts 只能承载 name / phone / email / company / position；industry / project / relation 只存在本地库
